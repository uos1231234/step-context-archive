# Context Archive（上下文归档与召回）

本技能是 context-archive 扩展的行为约定。扩展把即将被压缩掉的历史块
原文写入 stamp 归档文件，压缩后的会话里只保留带摘要的 #STAMP 索引行。
技能负责告诉模型：这些行是什么、什么时候必须召回、摘要按什么格式读。

## #STAMP 标记语义

压缩摘要的顶部协议段之后，每个历史任务块对应一行：

```
#STAMP <id> → <绝对路径> — <三点摘要>
```

- `<id>`：12 位十六进制 stamp，由块 key（或 toolCallId）哈希得到。
- `<绝对路径>`：归档文件位置，命名固定为 `stamp-<id>.md`，内容是该块
  被压缩前的**原文**（未经去重、未经截断）。
- `<三点摘要>`：索引性质的“背景—行动—结论”，**不是原文的可靠复述**，
  细节可能失真，一切以归档文件为准。
- 以 `[context-archive]` 开头的行是插件协议说明，不是任务内容。

## 召回纪律

1. 历史上下文被归档时，优先用 `recall_by_stamp` 工具或 `/recall-stamp <id>`
   命令按 stamp 召回全文，再基于原文回答。
2. 以下情况**必须召回**，禁止凭记忆复述：用户引用历史对话原话；需要精确
   的报错全文、堆栈、命令输出；需要被删除或被投影的代码片段；需要确认
   早前做出的决定及其上下文。
3. 以下情况**不必召回**：话题已经切换；信息在当前工作区文件里能直接读到
   （直接读文件）；用户明确表示不用翻历史。
4. 召回失败（文件缺失、stamp 非法）时，如实告知失败原因与尝试过的路径，
   不要编造“原文大概是……”。
5. 一次回答尽量按需召回所需的最少块，避免把全部归档灌入上下文。

## 三点摘要协议

每个归档块的摘要固定三点，每点一行、前缀依次为：

- `背景：` 当时为什么做这件事（任务来源、动机）。
- `行动：` 实际做了什么（关键改动、命令、文件路径）。
- `结论：` 结果与遗留问题（是否完成、未决项、下一步）。

要求：不复述日志与大段代码；保留关键文件路径、命令与数字；三点合计控制
在几行以内。摘要与原文冲突时，以 #STAMP 指向的原文为准。

## 压缩后行为约定

- 压缩完成后先读顶部 `[context-archive]` 协议头与全部 #STAMP 行，建立
  对“有哪些历史块、各自讲什么”的整体认知，再继续任务。
- 未完成任务、未决问题不得因压缩而遗忘；它们应出现在“结论”点或被用户
  重新提起后召回核实。
- 超大工具结果（超过投影上限，约 20K token）会在会话中被截断并标记投影，
  全文同样按 stamp 归档；需要工具输出细节时走同一召回路径。
- turn_end 钩子输出的 `[context-archive] usage=... decision=...` 诊断行写在
  stderr，不是用户消息，不需要回应。

## 典型场景示例

1. 用户问"上次那个报错的完整堆栈是什么"：#STAMP 摘要里只有一行结论——
   先用 recall_by_stamp 召回对应块，再基于原文堆栈作答。
2. 用户问"接下来该做什么"：读各块"结论"点即可推进，无需召回；只有结论
   含糊或与当前文件状态矛盾时才召回核实。
3. 发现某 #STAMP 摘要与工作区现状冲突：以归档原文和当前文件为准，向用户
   说明差异，不要静默采信摘要。
4. 召回的原文仍然很长：自行从中提取所需片段回答，不要把整块原文复述给用户。
## 适用与不适用边界

适用：长会话、跨多轮/多日的续接任务、工具输出巨大、需要精确历史引用。

不适用：短会话（从未触发压缩，没有 #STAMP 行）；一次性问答；信息可从当前
文件系统直接获得的场景（直接读文件比召回更可靠）；把本技能当作持久存储——
归档文件面向会话恢复，不应被当作跨项目知识库覆写。

## 相关接口

- 工具：`recall_by_stamp(stamp)` —— 读回归档原文。
- 命令：`/recall-stamp <stamp>`、`/context-archive`（诊断面板）。
- 归档位置：`archiveDir(<agentDir>)`，可用 `/context-archive` 查看实际路径。
